How DecentraCloud Works

A file-sharing system with no single point of trust: files are hashed with SHA-256 and replicated across three Google Cloud Storage buckets ("cloud nodes"), while every action is chained into a tamper-evident blockchain ledger.

System Architecture

Blockchain Hash-Chaining

Each block stores the hash of the block before it. Changing anything in an earlier block changes its hash — which breaks every link after it, making tampering instantly detectable.

Key Concepts (Viva Reference)

Plain-language meanings of the terms used in this project — useful when explaining the project to an examiner.

TermSimple meaningWhere it appears in this project
Local storageFiles saved on your own computer's disk (e.g. a folder like nodes/node_1). You maintain the hardware; it is tied to one machine.The original version of this project stored files in three local folders. Now only the optional offline dev mode (STORAGE_BACKEND=local) does this.
Cloud storageFiles stored on servers owned and operated by a cloud provider (here Google Cloud) and reached over the internet through an API.Files now live in three Google Cloud Storage buckets instead of local folders.
Cloud bucketThe basic container in cloud object storage — like a top-level folder. Buckets have a globally unique name and hold objects.GCS_BUCKET_NODE_1/2/3 — one bucket per storage node.
Cloud objectOne item stored inside a bucket: the bytes plus its name and metadata. Objects are immutable through normal writes (you replace them).Each upload creates an object named by its SHA-256 hash in every bucket, with metadata (owner, original filename, time).
ReplicationStoring the same data in several places so it is not lost if one copy dies.On upload, identical bytes are written to all three GCS buckets.
DecentralizationNo single machine/location holds the only copy — control and data are spread, so there is no single point of failure or trust.Three independent buckets + a separate ledger instead of one server folder.
BlockchainAn append-only list of blocks where each block stores the hash of the block before it, so history cannot be silently edited. (This project: a lightweight educational hash-chain ledger — not a cryptocurrency.)blockchain.py records REGISTER / UPLOAD / SHARE / DOWNLOAD / VERIFY events.
HashingA one-way function that turns any input into a fixed-length fingerprint. Easy to compute, practically impossible to reverse.SHA-256 of file content and of every block.
SHA-256A specific hash algorithm producing a 64-character (256-bit) hex string. Same input → same output; one bit changed → completely different output.Names every cloud object; stored in metadata, database and ledger blocks.
IntegrityData has not been altered — proven by re-computing the hash and comparing with the expected one.The Verify page re-downloads every copy and compares hashes; a mismatch shows "✗ Integrity Failed".
AuthenticationProving who you are (login: username + hashed password).Registration/login with Werkzeug password hashing.
AuthorizationDeciding what you are allowed to do after you are authenticated.Only the owner can share; only owner or shared users can download/verify.
Fault toleranceThe system keeps working when some components fail.If one node's copy is corrupted or the bucket is unreachable, the app automatically serves a healthy copy from another node.
